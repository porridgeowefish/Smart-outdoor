1. 目标表述

本轮目标不是让 RAG 直接判断“用户要简单路线”，而是识别用户话语中存在一个需要澄清的意图维度，再用标准标签和线路指标组织追问。

用户措辞希望线路比较简单
意图召回可能涉及体力、路面、导航、安全和服务
歧义判断“简单”无法唯一映射为一个标签
结构化追问你更在意哪种简单？
用户确认爬升少 + 路面清楚
标准写入指标约束 + preference/avoid tags

2. 现有标签体系能否直接使用

可以直接复用的部分

现有 TAG_TAXONOMY 已定义路线侧标准标签，例如铺装路、有路标、景区管理、补给、信号、下撤点、风景和人群。

不能直接承担的部分

它没有完整描述用户措辞、意图维度、正反表达、标签组合关系、追问方式和指标约束，因此还不是完整 RAG 知识库。

层次职责示例
路线标准标签库线路具有什么属性公路/铺装路、有路标、多个下撤点
客观指标可计算、可比较的技术事实距离、爬升、坡度、预计耗时
意图知识库用户措辞可能指向哪些维度“简单”可能是体力轻松、路好走、容易导航
选择卡模板把候选维度组织成可确认问题你更在意体力、路面还是导航？

3. “线路比较简单”如何处理

重要：“简单”不是一个足够精确的路线事实。系统不能直接把它等同于“铺装路”或“亲子友好”。
用户可能的真实意思对应数据可能的确认选项
体力轻松距离、爬升、预计时长、能力画像距离短 / 爬升少 / 时间短
路面好走terrain 标签铺装路 / 石板平路 / 常规土路
不容易迷路有路标、景区运营管理路标清楚 / 成熟景区路线
风险更低下撤点、信号、救援点、野路避开项可下撤 / 有信号 / 避开野路
服务方便补给、卫生间、交通设施有补给 / 有卫生间 / 交通方便

推荐追问

你说的“简单”更接近哪一种？
- 体力轻松：距离和爬升少
- 路面好走：尽量是铺装路、石板路或清晰步道
- 容易导航：有路标、成熟路线，不容易走错
- 更稳妥：有信号、下撤方便，避开野路
- 都希望有，优先帮我找综合轻松的

4. 用户确认后写到哪里

不建议所有答案都塞入 preference_tags。客观指标约束和标签偏好应分开。

用户确认建议写入
距离短、爬升少、一天内结构化指标约束，例如 distance/elevation/time preference
铺装路、石板平路、有路标preference_tags
不要野路、不要冰雪路、不要无信号avoid_tags
安全优先、体力轻松场景字段或强度偏好，同时结合能力画像

5. RAG 与 LLM 的职责

组件负责不负责
RAG从措辞召回意图维度、关联标签、避开项和追问模板直接替用户确认最终偏好
规则层判断是否有歧义、是否需要追问、允许写入哪些字段自由创造标签

Pydantic验证 choice_request 和答案结构理解业务语义
用户确认真正需求承担系统猜测造成的隐性结论
